## 1. 系统概述

### 1.1 业务定位

服务商系统是「九州社区生活服务平台」的核心业务模块之一，覆盖以下场景：

| 场景 | 说明 |
|------|------|
| **服务商入驻** | 用户提交服务商申请 → 管理员审核 → 创建服务商档案 |
| **服务商门户** | 服务商通过 Web 后台管理店铺、服务、订单、客户 |
| **技工管理** | 服务商查看社区内技工列表、统计技工业绩 |
| **财务结算** | 收入汇总、明细查询、余额查看 |
| **服务订单** | C 端用户下单 → 支付 → 服务商接单/派单 → 技工履约 → 完成 |
| **营销工具** | 服务商创建优惠券、查看发放统计 |
| **退款管理** | 服务商审批退款申请 |

### 1.2 技术栈

- **Runtime**: Node.js 18 + Express 5.x
- **ORM**: Sequelize 6.x + MySQL 8.0
- **Auth**: JWT (自定义 Payload，双令牌体系)
- **Payment**: 微信支付 V3 (JSAPI) + 虚拟支付（开发联调）

## 3. 认证体系

### 3.1 双令牌体系

服务商系统使用两种 JWT 令牌：

| 令牌类型 | 用途 | Payload 特征 |
|----------|------|-------------|
| **用户端 JWT** | 小程序/C 端用户登录 | `{ id, openid, token_version }` |
| **服务商门户 JWT** | 服务商 Web 后台 | `{ portal: 'service_provider', profile_id, provider_user_id, sp_account_id }` |

### 3.2 令牌换取流程

```
用户端 JWT ──► POST /service-provider-portal/token/exchange ──► 服务商门户 JWT
                    (需 authMiddleware, 即用户已登录)
```

换取条件：
1. 用户必须有 `status='approved'` 的 `ServiceProviderApplication`
2. 用户必须有 `status='active'` 的 `ServiceProviderProfile`
3. 若门户账号不存在，自动创建（`owner` 角色，随机密码）

### 3.3 登录流程

```
POST /service-provider-portal/login
Body: { username, password }

Response:
{
  errno: 0,
  data: {
    token: "<JWT>",
    profile: { id, shop_name, user_id, community_id },
    account: { id, username, role }
  }
}
```

### 3.4 认证中间件

**文件**: `src/middlewares/serviceProviderPortalAuthMiddleware.js`

支持两种验证路径：

1. **标准路径**: 解析 `portal: 'service_provider'` 的 JWT
2. **调试路径**: `DEBUG_SKIP_SP_PORTAL_TOKEN=1` 时，允许普通用户 JWT 直连，按 `user_id` 查询 `service_provider_profiles`

挂载到 `req.spPortal` 的对象：

```js
{
  profile_id: Number,       // 服务商档案 ID
  provider_user_id: Number, // 服务商用户 ID
  sp_account_id: Number     // 门户账号 ID
}
```

## 5. 订单状态机

### 5.1 状态定义

```js
const SERVICE_ORDER_STATUS_TEXT = {
  pending_pay:           '待支付',
  pending_accept:        '待服务商接单',
  pending_worker_accept: '待技工接单',
  paid_pending_dispatch: '待派单',
  dispatched:            '已派单',
  in_service:            '服务中',
  pending_user_confirm:  '待用户确认完成',
  completed:             '已完成',
  cancelled:             '已取消',
  closed:                '已关闭'
};
```

### 5.2 状态流转图

```
┌─────────────┐
│ pending_pay │◄──── 创建订单
└──────┬──────┘
       │ 支付成功
       ▼
┌─────────────────────────────────────────────────────────────┐
│ 支付后状态分支:                                              │
│ 1. 有 provider_user_id (直挂服务商) → pending_accept        │
│ 2. 有 assigned_worker_id (直约技工) → pending_worker_accept │
│ 3. 无服务商无技工 → paid_pending_dispatch                   │
└─────────────────────────────────────────────────────────────┘

【分支 1: 直挂服务商】
pending_accept ──► 服务商接单 ──► paid_pending_dispatch ──► 派单 ──► dispatched
                                                                    │
【分支 2: 直约技工】                                               ▼
pending_worker_accept ──► 技工接单 ──► dispatched ──► in_service
                                                      │
【分支 3: 平台派单】                                  ▼
paid_pending_dispatch ──► 派单 ──► dispatched ──► in_service
                                                    │
                                                    ▼
                                              in_service ──► 服务商/技工完成 ──► pending_user_confirm
                                                                                  │
                                                                                  ▼
                                                                            用户确认 ──► completed
```

### 5.3 支付状态流转

| 原状态 | 操作 | 新状态 | 条件 |
|--------|------|--------|------|
| `pending_pay` | 创建支付 | `pending_pay` | — |
| `pending_pay` | 支付成功 | `pending_accept` | `provider_user_id` 存在 |
| `pending_pay` | 支付成功 | `pending_worker_accept` | `assigned_worker_id` 存在 |
| `pending_pay` | 支付成功 | `paid_pending_dispatch` | 无服务商无技工 |
| `pending_accept` | 服务商接单 | `paid_pending_dispatch` | — |
| `paid_pending_dispatch` | 派单 | `dispatched` | — |
| `dispatched` | 开始服务 | `in_service` | — |
| `in_service` | 完成服务 | `pending_user_confirm` | `await_user_confirm=true` |
| `in_service` | 完成服务 | `completed` | `await_user_confirm=false` |
| `pending_user_confirm` | 用户确认 | `completed` | — |

## 10. 常见问题

### Q1: 模块化入口 (`src/app.js`) 和遗留入口 (`src/index.js`) 有什么区别？

**A**: 
- `src/index.js` 是遗留入口，直接挂载每个路由
- `src/app.js` 是模块化入口，通过 `src/routes/index.js` 统一挂载所有路由
- 两者应保持一致，当前已通过修改 `src/routes/index.js` 实现了路由对齐

### Q2: 为什么 `WorkerProfile` 没有 `service_provider_id` 字段？

**A**: 当前设计通过 `community_id` 匹配技工与服务商。同一社区的技工可被该社区的服务商查看和管理。如需绑定特定服务商，需后续扩展。

### Q3: 订单归属如何判定？

**A**: 通过 `serviceProviderOrderScope.js` 中的 `buildProviderOrderWhereClause`：
- 订单 `provider_user_id` 等于服务商 `user_id`
- 或订单的 `service_id` 属于该服务商发布的服务

### Q4: 支付回调如何处理？

**A**: 服务订单支付复用微信支付 V3 体系：
- 创建支付: `POST /service-orders/payments/create`
- 回调地址: `WX_PAY_NOTIFY_URL` 配置的地址
- 开发联调: `POST /service-orders/payments/mock-success`

### Q5: 如何创建服务商门户账号？

**A**: 三种方式：
1. **自动创建**: 用户通过 `token/exchange` 换取时，若账号不存在自动创建
2. **脚本创建**: `node scripts/seed-service-provider-portal-demo-account.js`
3. **Admin API**: `POST /admin/service-provider-portal-accounts`
