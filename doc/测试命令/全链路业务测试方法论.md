## 一、测试核心原则

### 1.1 四大支柱

```
┌─────────────────────────────────────────────────┐
│           全链路业务测试四大支柱                    │
├─────────────────────────────────────────────────┤
│                                                 │
│  1. 角色驱动测试                                  │
│     每个业务场景都需要考虑所有相关角色              │
│     用户 → 商家 → 技工 → 服务商 → 推客 → 管理员   │
│                                                 │
│  2. 数据先行原则                                  │
│     无数据 = 无法测试                              │
│     必须先创建完整测试数据才能验证业务链条           │
│     例如:邻里帮帮订单需要先创建用户和小区数据        │
│                                                 │
│  3. 链条闭环验证                                  │
│     每个操作都要验证上下游影响                      │
│     发布帮帮订单 → 邻居抢单 → 完成服务 → 用户确认  │
│                                                 │
│  4. 前后端同步测试                                 │
│     不只是前端页面,也不只是后端接口                  │
│     前端发布 → 后端接收 → 数据库同步 → 前端拉取     │
│     例如:帮帮订单发布后应能同步到数据库订单池        │
│                                                 │
└─────────────────────────────────────────────────┘
```

### 1.2 关键问题总结

| 问题类型 | 表现 | 教训 |
|---------|------|------|
| **数据缺失** | 店铺列表为空、订单无法测试 | 必须先创建测试数据 |
| **格式不一致** | API返回`{code,data}`和直接返回数据混用 | 需要统一解析逻辑 |
| **认证限制** | 用户登录需要真实微信code | 测试环境需要Mock登录 |
| **隐藏接口** | 二级页面接口需要前置触发 | 需要探索式测试 |
| **外键约束** | 创建订单时关联表不存在 | 需要了解数据库结构 |
| **前后端不同步** | 前端发布成功但数据库无记录 | 必须验证数据持久化 |
| **消息未触发** | 订单状态变化但无通知 | 必须验证消息系统 |
| **权限隔离** | 跨小区能看到别人订单 | 必须验证数据隔离 |
| **状态机不完整** | 订单状态无法流转 | 必须验证所有状态转换 |

### 3.2 API调用工具函数

```javascript
function api(method, path, body=null, token=null) {
  return new Promise((resolve, reject) => {
    const u = new URL(path, BASE_URL);
    const o = { 
      hostname: u.hostname, 
      port: u.port, 
      path: u.pathname + u.search, 
      method: method,
      headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json'
      }
    };
    if(token) o.headers['Authorization'] = `Bearer ${token}`;
    
    const req = http.request(o, (res) => {
      let data = '';
      res.on('data', chunk => { data += chunk; });
      res.on('end', () => { 
        try {
          resolve({
            s: res.statusCode,
            d: data ? JSON.parse(data) : {},
            r: data
          });
        } catch(e) {
          resolve({ s: res.statusCode, d: {}, r: data });
        }
      });
    });
    req.on('error', reject);
    if(body) req.write(JSON.stringify(body));
    req.end();
  });
}

## 四、核心业务链条测试设计

### 4.1 邻里帮帮全链路 【重点 - 前后端同步测试】

**场景**: 用户发布代办请求，邻居接单完成

**核心逻辑**: 用户发布订单 → 订单同步到数据库 → 订单进入小区订单池 → 同小区邻居可见 → 邻居抢单 → 完成服务 → 用户确认 → 消息通知全流程

```
完整步骤:
1. [用户A] 发布帮帮订单   POST   /neighbor-assist
   请求体: { community_id, category, content, address, time, images }
   
   验证点:
   ✓ 后端接收并创建订单记录
   ✓ 数据库neighbor_assist_orders表新增记录
   ✓ 订单community_id与用户community_id一致
   ✓ 订单状态为pending(待接单)
   ✓ 前端发布成功提示

2. [用户A] 查看我的帮帮订单 GET    /neighbor-assist/my
   
   验证点:
   ✓ 能查到刚发布的订单
   ✓ 订单状态正确显示
   ✓ 订单详情完整(分类、内容、地址)

3. [用户B-同小区] 查看可抢订单池 GET    /neighbor-assist/pool
   参数: { community_id, page, limit }
   
   验证点:
   ✓ 能看到用户A发布的订单
   ✓ 只能看到同小区的订单(数据隔离)
   ✓ 订单列表按时间倒序排列

4. [用户B-异小区] 查看可抢订单池 GET    /neighbor-assist/pool
   
   验证点:
   ✓ 不能看到用户A发布的订单(跨小区隔离)
   ✓ 只能看到自己小区的订单

5. [用户B] 抢单         POST   /neighbor-assist/:id/grab
   
   验证点:
   ✓ 订单helper_id更新为用户B的id
   ✓ 订单状态变更为grabbed(已抢单)
   ✓ 用户A收到消息通知(订单被接单)
   ✓ 用户A的"我的帮帮订单"中状态更新
   ✓ 用户B的"我的帮帮订单"中显示该订单

6. [用户B] 完成服务       POST   /neighbor-assist/:id/complete
   
   验证点:
   ✓ 订单状态变更为completed(已完成)
   ✓ 用户A收到消息通知(服务已完成)
   ✓ 用户A的"我的帮帮订单"中状态更新

7. [用户A] 确认完成      POST   /neighbor-assist/:id/confirm (如果有此接口)
   
   验证点:
   ✓ 订单状态变更为confirmed(已确认)
   ✓ 用户B收到完成确认通知

8. [用户A] 评价         POST   /neighbor-assist/:id/review (如果有此接口)
   
   验证点:
   ✓ 评价成功保存
   ✓ 用户B的评价记录更新

关键验证:
✓ 前后端数据同步: 前端发布 → 后端接收 → 数据库持久化 → 前端拉取一致
✓ 小区隔离: 不同小区用户只能看到自己小区的订单
✓ 消息通知: 订单状态变化时触发对应通知(接单通知、完成通知)
✓ 订单管理: 类似于技工工作台,用户有完整的订单管理功能
✓ 状态机完整性: pending → grabbed → completed → confirmed
```

```

## 七、问题排查指南

### 7.1 常见问题及解决方案

| 问题 | 可能原因 | 解决方案 |
|-----|---------|---------|
| 订单发布成功但数据库无记录 | 后端未持久化 | 检查后端controller是否有db.save() |
| 抢单后发布人无通知 | 消息系统未触发 | 检查订单状态变化时是否调用消息服务 |
| 跨小区能看到订单 | 查询未过滤community_id | 检查SQL查询是否有WHERE community_id=? |
| 订单状态无法流转 | 状态机逻辑错误 | 检查状态转换条件是否满足 |
| 图片上传失败 | 路径配置错误 | 检查uploads目录权限和配置 |
| 购物车数据丢失 | 未持久化到数据库 | 检查是否有cart_items表 |
| 支付成功但订单未更新 | 支付回调未处理 | 检查支付回调接口 |

## 九、最佳实践总结

### 9.1 测试原则

1. **数据先行**: 必须先创建完整测试数据才能验证业务链条
2. **角色驱动**: 每个业务场景都要考虑所有相关角色
3. **链条闭环**: 每个操作都要验证上下游影响
4. **前后端同步**: 前端发布 → 后端接收 → 数据库同步 → 前端拉取
5. **消息验证**: 订单状态变化必须验证消息通知
6. **隔离验证**: 必须验证数据隔离(小区隔离、角色隔离)

### 9.2 测试工具

- API测试: 使用Node.js http模块或Postman
- 数据库验证: 使用MySQL命令行或Navicat
- 前端测试: 使用微信开发者工具
- 日志监控: 使用tail -f查看后端日志

### 9.3 常见问题预防

1. **数据缺失**: 提前准备测试数据脚本
2. **格式不一致**: 统一API返回格式解析逻辑
3. **认证限制**: 准备测试环境Mock登录
4. **隐藏接口**: 定期探索前端API文件和后端路由
5. **前后端不同步**: 每个操作都验证数据库状态
6. **消息未触发**: 每个状态变化都验证消息通知
