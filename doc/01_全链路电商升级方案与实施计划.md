# 社区小程序 - 全链路电商与用户体系升级大纲及需求文档

*(此文档基于最新多轮需求探讨及反馈确认后生成，用于指导新一轮的开发和联调)*

## 一、开发核心策略与决策清单

根据目前的系统约束与业务需求，我们的重构与开发策略已做如下拍板确认：

1. **统一短信验证码开发与测试标准**：
   - 现状：目前暂无真实的可发短信实体硬件/服务。
   - 决策：明确告知后端，在处理例如“注册”、“重置密码”、“手机快捷登录”等需要请求发送短信并在表单附带回传参数的所有接口中，**将所有短信验证码白名单临时写死默认为 `024680`**。前端联调时也一律下发并校验该万能码。
2. **明确并强化【多商户平台体系】定位**：
   - 决策：商城不设自营底仓售卖。这意味着，在我们的前台用户购买了商品，进入到履约/售后（待收货、维权、退款中）阶段时，点击“联系商家”等维权客服按键，后台下发的一定是各自门店入驻时的留存电话或负责人电话，而非官方 400 统一电话。
3. **坚决剥离受限支付方式，保留纯血能力**：
   - 决策：在“订单确认/收银台”业务逻辑处，仅保留【微信原生支付】（拉起 `wx.requestPayment`）一种流派。剔除原生小程序下容易遭到封禁、链路极差拦截极高的支付宝H5通道。
4. **柔性的“随便逛逛”游客放行制**：
   - 决策：为降低拉新流失，微信内第一次唤起并一键拿走手机号后，不跳转绑定密码页面干扰购物。用户一进来便处于“游客免打扰（无密先畅游）”状态，任选逛街模式，直至他们进入购买或资金结算等“硬拦截”关卡，再索要完整的补全机制。

## 二、前后端功能升级需求详情单

### 模块一：身份与认证模块重建
* **前端变动任务**：
  - 新建完全独立的 `login/login` (账密登入框体系)、`register/register` (手机、图形地图选址、确认密码)、`forget-password/forget-password` (短信重校验) 三大门户页。
  - 维护并引入富文本“平台注册协议”至页尾。
  - 更新现有的 `user-edit` 页内录入实名字段框(`real_name`)。
* **发给后端的开发诉求**：
  - `Users` 核心表扩展出真实姓名、加密盐值哈希密码机制。
  - 基于第一大点的决策，开放不必须验证真实短信服务器的一套鉴权接口（`Post /register` 等），只用看 `code: "024680"` 即可下发合规用户的认证长周期 Token。
  - 需要保障对无 Token 即 `Cookie/Bearer` 空包用户的部分查询通道豁免放行。

### 模块二：商城与售卖体系扩容
* **前端变动任务**：
  - **救活被占据的购物车系统**：彻底重做 `goods-cart` 结构。引入勾选状态流、多商店分组流、以及加减底栏拦截及批量抹除。
  - **商品结果与排序组件**：打造带有【价格降升】、【销量降降】的真列表筛选器。
  - **商户与商品隔离列表**：引入顶栏的输入模式下拉组件或在原生搜页分出（寻产品 vs 寻店铺）双核导向。
  - **选型与参数**：对现有粗糙的详情页重装加入重型“Bottom Sheet”类 SKU 规格抽屉控件。
* **发给后端的开发诉求**：
  - 在 `Goods` 表的背后关联建立一整棵关于此货的 `Variants`（SKU组合树），以支持同一个商品在蓝色的 XL 卖50块，在红色的 XXL 卖80块并单独限制子项仓库的实体库存值。
  - 开辟针对 `Cart` 的数据库储存记录模型，支撑跨设备的用户选购件漫游。

### 模块三：维权与反向交易链路引擎（极重）
* **前端变动任务**：
  - 在大结算页 `goods-confrim` 中引入选择框以判定这单子究竟是快递发送（显示0+真实运费）或是“网格化同城提货”（跳出自提人、预约到访日期段、绑定预置手机）。
  - 对用户主页“家购物订单”过滤拦加入并拓展枚举映射。增加并匹配回传“待接单/备货中”、“已退款”状态到请求流。
  - **创建全新退款及跟单页**：新增 `after-sale-apply` 上传照片回退原因，和 `order-logistics` 进度轮播物流组件展示。
* **发给后端的开发诉求**：
  - 【售后退款表】：支持独立退款单 ID 的分配并脱胎于主体大单据ID。为了不引起后续分账乱账，强烈建议后台一定要支持订单明细里【某个单项货物的局部退单切块】，而不是必须选择全包粗放处理。
  - 在微信侧支付对接收银的底层 SDK 时，请确信已准备好了对应的统一下了退款证书与 `Refund` 调用方法支撑原路清退。

## 四、后端 API 交互示例（阶段一：注册与登录）

**1. 发送注册验证码（约定的万能码体系）**
- URL: `POST /api/auth/sms/send`
- Request:
  ```json
  {
    "phone": "13800000000",
    "type": "register" // 或 "forget_password"
  }
  ```
- Response: 成功即可，前后端均知晓验证码应为 `024680`。

**2. 账号密码注册接口**
- URL: `POST /api/auth/register`
- Request:
  ```json
  {
    "phone": "13800000000",
    "code": "024680",
    "password": "hashed_or_plain_password",
    "address": "浙江省杭州市西湖区某某街道",
    "lat": 30.274085,
    "lng": 120.15507
  }
  ```
- Response: 
  ```json
  {
    "token": "JWT_TOKEN_STRING",
    "user": {
      "id": 123,
      "phone": "13800000000"
    }
  }
  ```

**3. 短信重置密码接口**
- URL: `POST /api/auth/password_reset`
- Request:
  ```json
  {
    "phone": "13800000000",
    "code": "024680",
    "new_password": "new_hashed_password"
  }
  ```

**5. 全能搜索聚合接口（商品+店铺）**
- URL: `GET /api/market/search`
- Request:
  ```json
  {
    "keyword": "苹果",
    "type": "goods", // 或 "shop"
    "sort": "smart", // smart(综合排序), rating(好评优先), price_asc(价格偏低), sales(销量优先)
    "page": 1,
    "page_size": 20
  }
  ```
- Response: 对应下发带格式包裹列表 `list`，如 `goods` 会带销量，`shop` 会带商品缩略图和店铺信息。

**6. 核心品类配置表（Category）管理与初始化**
- **逻辑补充与数据库要求**：
  前台已按照要求，将具有电商及实体服务属性的十宫格类目迁移至【本地集市】的顶部滑块区域。
  这 10 个标准大类名现已在前端硬绑定，分别为：
  `["食品生鲜", "美妆洗护", "居家百货", "服装箱包", "母婴系列", "家用电器", "数码产品", "珠宝饰品", "旅游出行", "传统工艺"]`
  **致后端/DBA**：请务必在商户系统（`Shops`表）或其关联的品类库字典（`Categories`表）中同步新增并维护这 10 个**一字不差的同名父级分类字典数据**。前端调用商城搜索及检索集市商家时，将直接以这 10 个中文全称作为 `category` 聚合字段执行条件过滤。

## 六、购物车独立解耦机制与状态流转（O2O外卖模式）

- **独立购物车模式**：本系统明确为 **外卖/O2O 店铺独立模式**。这就意味着用户的“跨店购物车”概念不被允许，每次只能选取一家店铺的商品进入它的专属购物车结构结算。
- **购物订单状态机变更**：由于偏向外卖即时零售范畴，前端我的“购物订单”生命周期已从传统的“发货制”变更为“服务接单制”。核心 `status` 枚举约定变更为：
  1. `pending_payment`（待付款）
  2. `pending_accept`（待接单）
  3. `pending_service`（待服务/备货中）
  4. `pending_receipt`（待收货）
  5. `completed`（已完成）
  6. `cancelled`（已取消）
  7. `refunded`（已退款）

## 八、第三阶段：混合模式 SKU 选配与单店独立购物车重构（执行中）

**1. 架构选型决议：方案 C（混合极速模式）**
系统采用 “单品富文本大详情” + “单店悬浮小推车” 结合的设计原则：
- **无全局购物车**：全面废弃入口级别的统一大购物车（`pages/goods-cart` 原型作废降级）。
- **单店小推车（Drawer）**：购物车数据根据 `shop_id` 进行存储和隔离。当用户在 A 店的商品详情页点开“购物车”时，只会从底部向上滑出一个弹窗抽屉，展示在 A 店添加的所有商品。直接点击“去结算”即可提交 A 店的订单。
- **SKU 属性库引入**：商品详情结构增加 SKU 属性树结构。

**2. 前端请求明细约定 (前端所需结构)**
- 获取商品详情带 SKU ( `GET /api/market/goods/detail` ):
  ```json
  {
    "id": 1001,
    "shopId": 88,
    "shopName": "王大妈蔬菜店",
    "name": "多规格水果拼盘",
    "main_images": ["url1", "url2"],
    "price_range": "20.00-45.00",
    "sales": 1200,
    "desc_html": "<p>商品介绍图文</p>",
    "sku_tree": [ 
      { "group": "规格", "items": ["大份", "小份"] },
      { "group": "口味", "items": ["偏甜", "偏微酸"] }
    ],
    "sku_list": [
      { "id": "sku_1", "specs": ["大份", "偏甜"], "price": "45.00", "stock": 10, "image": "..." },
      { "id": "sku_2", "specs": ["小份", "偏微酸"], "price": "20.00", "stock": 5, "image": "..." }
    ]
  }
  ```

**3. 购物车 Storage 本地机制**
出于外卖高并发和快速响应的需求，购物车数据按 `cart_${shop_id}` 为键值直接存在小程序本地缓存中。仅当用户点击“去结算”时，才将选好的 `[{sku_id, quantity}]` 提交给订单确认页生成账单。极大降低服务器交互冗余。

**4. 提交订单接口规范**
- 用户于确认收银台完成点击后，发起创单请求 ( `POST /api/market/order/create` ):
  - `shop_id`：归属源店铺
  - `delivery_mode`：配送类型支持两套枚举 (`express` 到家 / `pickup` 自提)
  - `address`：完整的收货地址对象（若 `express` 时为必填）
  - `items`：具体选购规格组 `[{sku_id: '...', goods_id: '...', quantity: 2}]`
  - `remark`：买家留言
- 创建完成后服务端立刻生成 `orderNo` 并返回，前端清空对应该店铺的 `cart_${shop_id}` 本地缓存（若属于购物车买单渠道）并重定向至新版 `market-order-detail` 发起微信支付验证。
