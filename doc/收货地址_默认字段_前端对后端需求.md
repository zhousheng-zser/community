# 收货地址「默认」标识 — 前端对后端需求说明

> 口吻：前端研发提出，供后端建表、接口与数据修复对齐。  
> 关联文档：`API_DOC.md` §8.4、`家集市店铺化_FE-BE沟通纪要_08_BE.md`

---

## 1. 是否需要库表字段？

**需要。**  

请在 **用户收货地址表**（如 `user_addresses`）对**每一条地址**持久化「是否为默认收货地址」，用 **布尔或 0/1** 均可，与现有项目风格一致即可。

推荐字段名（二选一，接口与文档统一即可）：

| 方案 | 字段名（库表 / JSON） | 说明 |
|------|----------------------|------|
| A（与当前小程序请求体对齐） | `is_default` | 下划线，与部分已有 Node 习惯一致 |
| B（与当前小程序部分展示字段对齐） | 在 JSON 中同时兼容 `isDefault`（camelCase） | 若全链路统一一种命名，请在 `API_DOC` 里写死一种 |

**约束：**

1. **同一用户同一时间只能有 0 或 1 条** `is_default = true`（或 `1`）。  
2. **用户仅有 1 条地址时**，该条 **必须** 为默认（`is_default = 1`）。建议在：  
   - 新增第一条地址成功时由服务端置默认；  
   - 或定时/登录后校验任务：若 `COUNT(*)=1` 则自动把该条更新为默认。  
3. 删除当前默认地址后，若仍有其他地址，需 **指定新的默认**（例如按更新时间取最近一条，或约定规则写进接口文档）。

前端已做 **弱兜底**（仅一条时展示与家集市逻辑按默认处理），但 **以数据库为准** 才能避免换端、清缓存、重新登录后状态不一致。

---

## 2. 接口约定（摘要）

### 2.1 `GET .../user/addresses`（列表）

- 每条返回中 **必须包含** 默认标识，例如：  
  `"is_default": true` 或 `"is_default": 0`  
- 若历史数据未维护该字段，请 **补迁移** 并按 §1 规则回填。

### 2.2 `POST .../user/addresses`（新增）

- 请求体支持 `is_default` / `isDefault`（与你们统一命名一致）。  
- **首条地址**：前端会传 **`is_default: true`**；后端应落库并保证唯一默认。

### 2.3 `PUT/PATCH .../user/addresses/:id`（更新）

- 若将某条设为默认，请 **将该用户其他地址的默认标清除**，保证唯一性。

### 2.4 `POST .../user/addresses/:id/default`（若存在独立接口）

- 行为与「更新为唯一默认」一致即可。

---

## 3. 与「重新登录 / 无 GPS」的关系（给后端的产品语义）

- 小程序在 **拿不到实时定位** 时，会用 **默认收货地址的经纬度**（若已保存）参与家集市等逻辑。  
- 若 **没有默认地址字段** 或 **始终为 false**，则前端无法与后端、用户认知对齐（例如列表里只有一条却仍显示「未设默认」）。  
- **经纬度** 仍建议单独字段（如 `latitude` / `longitude`），与「是否默认」无关；无经纬度时前端无法把该地址当作地图坐标使用。

---

## 4. 验收建议

1. 新用户新增第一条地址后，DB 中该条 `is_default=1`，列表接口返回为 `true`。  
2. 仅有一条地址的老用户，迁移后同样为默认。  
3. 设置另一条为默认后，原默认条自动为 `0`。
